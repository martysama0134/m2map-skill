# `shadowmap.raw` + `shadowmap.dds` — Baked Terrain Shadows

Per-sectree baked shadow data, generated by the WorldEditor from a top-down shadow render. Two files with the same content in different encodings:

- **`shadowmap.dds`** — texture the client multiplies over terrain when rendering.
- **`shadowmap.raw`** — CPU-side copy used for sampling shadow color at a point (`GetShadowMapColor`, e.g. character shading).

Both are **generated artifacts** — a map editor only needs to read them for display and can regenerate or preserve them on save.

- **Path:** `<map>/<XXXYYY>/shadowmap.raw`, `<map>/<XXXYYY>/shadowmap.dds`
- **Source:** load `CTerrain::LoadShadowMap` (`GameLib/AreaTerrain.cpp:104-130`); save `SaveShadowFromD3DTexture9` (`WorldEditor/DataCtrl/MapAccessorTerrain.cpp:1284-1411`)

## `shadowmap.raw`

| Property | Value |
|---|---|
| Size | always **131,072 bytes** = 256 × 256 × 2 (strictly validated on load) |
| Layout | headerless, row-major `uint16`, little-endian |
| Pixel format | **RGB555**: bit 15 unused, bits 14–10 = R5, 9–5 = G5, 4–0 = B5 |
| Resolution | 256×256 = one texel per attr cell (1 m) |
| Default | all `0xFFFF` (white = unshadowed) when file absent |

Decode (`PRTerrainLib/Terrain.cpp:298-318`):

```js
const sm = new Uint16Array(await file.arrayBuffer()); // 65536 words
const texel = sm[y * 256 + x];
const b = (texel & 0x1f) << 3;
const g = ((texel >> 5) & 0x1f) << 3;
const r = ((texel >> 10) & 0x1f) << 3;
```

Note: an in-source comment claims "R5 G6 B5" but the actual decode masks 5 bits per channel — it is RGB555. The WorldEditor also writes RGB555 (`((r>>3)<<10) | ((g>>3)<<5) | (b>>3)`, `MapAccessorTerrain.cpp:1394`).

Observable engine quirk: the client's CPU sampler `GetShadowMapColor` assembles its return value as `(G<<16)|(G<<8)|R` — green duplicated into red, blue discarded (`Terrain.cpp:317`). For grayscale shadow data (the normal case) this is invisible; document readers replicating engine behavior byte-for-byte should mimic it, everyone else should decode the stored RGB555 faithfully as above.

Written **vertically flipped** relative to the D3D render surface (writer iterates rows bottom-up), so row 0 of the file is the *north* edge, consistent with height/tile grids.

## `shadowmap.dds`

Standard DDS written by `D3DXSaveSurfaceToFile`: 4-byte magic `"DDS "` + 124-byte header + pixel data.

- Format: uncompressed **X8R8G8B8**, 256×256, no mips → 128 + 262,144 = **262,272 bytes** (map_a2 verified).
- Some maps carry differently-encoded DDS here (e.g. `metin2_map_n_flame_01`: 43,832 bytes = compressed/mipped variant produced by other tools). **Parse the DDS header, don't assume the format.**

## Generation (WorldEditor)

Shadow pass renders the sector top-down into a 1024×1024 X8R8G8B8 target (`ShadowRenderHelper.cpp`), downsampled to 256×256, then: `.dds` saved directly; `.raw` written row-flipped as RGB555. Stale `shadowmap.tga` / `shadowmap.bmp` files (older format vestiges) are deleted on save.

## Pitfalls

- Both files must stay in sync — the client uses `.dds` for terrain rendering and `.raw` for point sampling.
- Loader rejects `.raw` of any size other than 131,072 bytes.
- Missing files are non-fatal (terrain renders unshadowed).
